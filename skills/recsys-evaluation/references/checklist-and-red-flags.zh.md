# 完整檢查清單與警訊

英文版 [checklist-and-red-flags.md](checklist-and-red-flags.md) 為執行規範。

這是 `SKILL.md` 中檢查清單與警訊表的完整版，列出每個問題防止的失誤，以及每個警訊的檢查方式。第 18 題起
依據 `lessons-learned.zh.md` 後段的教訓，延伸 `SKILL.md` 的檢查清單。

## 決策檢查清單

| # | 問題 | 防止的失誤 |
|---|---|---|
| 1 | 研究問題用一句話怎麼寫？使用者是已有歷史的使用者，還是未見過的使用者？ | 切分在不知不覺中回答了另一個問題 |
| 2 | 每個方法在推論時可以讀什麼（自己的歷史、商品文字、跨使用者統計），訓練時用了什麼（沒有訓練、其他領域、目標領域的訓練資料）？ | 跨資訊取用層級比較方法，卻沒有說明 |
| 3 | 哪一種切分回答問題 1：逐人 LOO、全域時間、使用者隔離，還是隨機？它允許哪一種洩漏，影響哪些方法？ | 未揭露的洩漏，或刪掉有效證據的防護 |
| 4 | 是否有方法跨使用者擬合參數或統計量？沒有的話，全域截止點不保護任何東西；有的話，規劃全域時間切分的敏感度檢查，或揭露跨使用者的未來資料 | 對凍結方法過度修正；斷言固定的洩漏方向 |
| 5 | 若使用使用者隔離切分：問題是否為未見過使用者的泛化？ID embedding 模型如何 fold-in 新使用者？ | 意外變成冷啟動評估 |
| 6 | 目標怎麼選？（最後一筆事件；不取「截止點後第一筆事件」） | 目標偏向較長的事件間隔（Gusak et al. 2025, §4.2） |
| 7 | 該資料集與版本有沒有官方切分檔？有的話使用，並記錄雜湊值 | 自行建立的 5-core 資料與公開切分不同 |
| 8 | 重複（使用者，商品）的規則、時間戳記同時間的處理規則（依原始列順序，不用商品 ID）、k-core 的順序，是否寫下？ | 重複商品造成的捷徑；以 ID 排序同時間事件造成的假序列 |
| 9 | 候選：全排序、抽樣 1+n（均勻或依熱門度），還是檢索後重排？主張是否限定在該分布？ | 抽樣指標使模型次序反轉（Krichene & Rendle 2020; Hidasi & Czapp 2023 §2.4） |
| 10 | 兩階段評估：檢索器是否固定、是否報告端到端指標、是否計入檢索失誤、目標是否從未補進候選？ | 被高估的重排分數 |
| 11 | 所有方法是否收到相同的使用者、目標與候選集合，以及協定規定共用的可見歷史與商品文字，並以逐題雜湊值驗證；其他輸入差異是否都標明為條件？ | 彙總表隱藏了不相等的證據 |
| 12 | 各方法每題的可見歷史筆數是否相等（商品目錄篩選可能只讓 ID 模型少掉歷史商品），或差異已宣告並標明？ | 一個方法看得到另一個方法看不到的歷史 |
| 13 | 確認階段主張的各類方法 seed 與重複次數（篩選階段可以只跑一次，用來決定下一個實驗）；「確定性」方法是否做過確定性檢查？ | 單次執行的雜訊被當成差異 |
| 14 | prompt 或方法變體在哪裡調整，報告用的使用者是否為新的使用者？ | 選擇偏差（winner's curse，贏家詛咒：從多個變體挑出最佳者，因而高估表現） |
| 15 | 失敗政策：執行失敗是否重跑；方法失敗是否保留為效用 0 並計數？ | 把當機當成結果，或剔除失敗而高估分數 |
| 16 | LLM 方法：候選順序、解析失敗、文字欄位、字詞與類別對照、歷史對調對照、相同快取條件下的成本、預訓練曝光？ | 增益其實來自位置、字詞重疊或記憶 |
| 17 | 抽樣結果旁是否列出隨機排序的期望值？ | 把接近隨機的分數誤認為排序能力 |
| 18 | 負例是否由設定 seed 的均勻隨機產生器抽出（或用目標也滿足的規則），且抽樣規則的任何函數都無法把目標排得比隨機好？ | 抽樣器洩漏了目標（第 18 則） |
| 19 | 商品識別碼是否完全不出現在模型請求中？只看識別碼的規則，分數是否接近隨機？ | 透過識別碼順序走捷徑（第 19 則） |
| 20 | 每個訓練式基線是否依照其來源的 selection 或 refit 做法，並在協定中寫明？ | 來源從未產生過的 refit 結果列（第 20 則） |
| 21 | 驗證使用者採抽樣時，樣本是否符合協定（選參可讀取被評估使用者的驗證事件時（例如逐人 LOO 或全域時間切分）包含他們，使用者隔離協定下排除他們），並共用同一個樣本檔？ | 基線在不同的母體上做選定，或被評估的使用者進入選參（第 21 則） |
| 22 | 稽核提出的每個高嚴重度協定問題，是否在主張定案前都已用實驗回答？ | 審稿後期才出現的主要反對意見（第 22 則） |
| 23 | 方法若讀取請求時間的跨使用者資訊：是否有全域切點檢查，把切點之後的事件從每個方法移除，並至少有一個考慮時間的訓練式基線？ | 把資訊不對等歸功於方法（第 23、24 則） |
| 24 | 報告用使用者群的曝光紀錄，是否已在先前的執行與姊妹專案中清查過？ | 「保留」的使用者群其實影響過先前的選擇（第 25 則） |
| 25 | 冷啟動或新商品的主張：依協定確切的時間與同時間規則，有多少目標符合條件？ | 主張所依據的符合條件目標很少或沒有（第 26 則） |
| 26 | 方法若讀取請求時間的活動資訊，是否在均勻負例旁一併報告時間對齊的負例變體？ | 增益來自請求時間沒有活動的負例（第 27 則） |
| 27 | LLM 基線：是否有官方設定，並在限制會造成影響時加上標示清楚的放寬變體？重新生成輪數與解析器是否在執行前宣告？ | 不忠於來源，或事後調整的 LLM 基線（第 28、29 則） |

## 警訊

| 觀察 | 可能原因 | 檢查 |
|---|---|---|
| 訓練式基線遠低於簡單規則 | 測試使用者未進訓練（使用者隔離或截止點），或基線未調參 | 計算每位評估使用者的訓練事件數；與官方程式碼的預設值比較 |
| 草稿寫「洩漏只對基線有利」 | 未經量測就斷言方向 | Ji et al. 表 5；做全域時間切分的敏感度檢查 |
| Popularity 低於隨機 | 依熱門度抽樣的負例 | 比較均勻與依熱門度抽樣；改用全排序 |
| 方法次序在 1+99 與全排序之間反轉 | 抽樣指標不一致 | 報告全排序或兩階段端到端 |
| 使用者／商品筆數與官方 benchmark 不同 | 去重與 k-core 順序、不同的資料版本 | 使用官方切分檔；記錄雜湊值 |
| 目標出現在可見歷史 | 保留了重複，或同時間處理錯誤 | 重複規則；嚴格的（時間戳記，原始列順序）切分 |
| 不同使用者的歷史相同 | 同時間事件依商品 ID 排序 | 同時間事件依原始列順序排序 |
| 重排指標高於檢索器召回率所允許的上限 | 目標被補進檢索清單 | 重新計算端到端指標，檢索失誤記為 0 |
| 分數與描述長度或清單位置相關 | 文字長度或位置偏差 | 文字欄位對照；順序置換 |
| 逐人挑最佳變體帶來大幅增益 | 用目標挑選的上限值 | 只報告可部署的選擇器 |
| 記錄檔中有記憶體不足或 HTTP 500，且效用為 0 的查詢 | 執行失敗被當成方法失敗 | 重跑到成功；分開計數 |
| 凍結模型在相同的執行之間分數不同 | 非確定性的 kernel 或服務 | 先做確定性檢查，再宣稱一次執行就足夠 |
| 依候選雜湊值或 ID 的規則排序時，目標排第一 | 負例由目標不滿足的規則選出 | 改用均勻隨機重抽負例；把該規則當成排序器測試 |
| 識別碼順序規則在候選池上勝過隨機 | 識別碼依時間順序分配 | 從請求中移除識別碼；把該規則列為捷徑檢查 |
| 改用時間對齊的負例後，方法增益縮小 | 均勻負例在請求時間沒有活動 | 兩種負例變體都報告 |
| 基線結果列讀的是來源不會訓練的 refit 模型 | refit 步驟不在來源做法之內 | 對官方程式碼做實務查核；把 refit 結果列標記為已被取代 |
| 多數「新」目標其實已有互動 | 沒有依定義計數 | 依協定的時間與同時間規則計算符合條件的目標 |
