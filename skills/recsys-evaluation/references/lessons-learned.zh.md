# 經驗教訓

英文版 [lessons-learned.md](lessons-learned.md) 為執行規範。

整理自一個研究專案。該專案在公開的電商與評分資料集上，比較凍結、免訓練的語言模型推薦器、訓練式推薦器與 LLM 排序器。每一則經驗列出沿用的假設、失誤如何浮現，以及由此產生的規則。

### 1. 沿用的切分沒有對照研究問題檢查

- 假設：專案規格要求使用者隔離切分加全域時間截止點，「以防止洩漏」；實作時照規格執行。
- 如何浮現：有合作者問，為什麼訓練式基線的分數這麼低。訓練式基線從未看過評估使用者的歷史，因此比較量測的是未見過使用者的表現，凍結方法卻在推論時讀取每位使用者的歷史。
- 影響：該協議下所有訓練式基線的結果，都是在對基線不利的條件下評估，不能支持「凍結方法追平訓練式基線」的主張。所有結果必須在新協議下重跑。
- 規則：實作切分之前，用一句話寫下研究問題，並檢查每個方法的訓練與推論輸入是否與它一致。

### 2. 比它要防止的洩漏更強的協議規則，會改變研究問題

- 全域截止點針對的是訓練集中的跨使用者未來資料。凍結方法只讀使用者自己較早的事件，沒有這個管道。對它套用截止點，只會刪掉有效的歷史。
- 把基線的訓練資料限制在截止點之前的事件，使很大比例的評估使用者完全沒有訓練事件，任務因此再次變成冷啟動評估。
- 規則：對每一項防護，寫出洩漏管道、哪些方法有這個管道，以及該規則移除的是否多於那個管道。修正本身會改變任務時，揭露洩漏，不做過度修正。

### 3. 以「截止點之後第一個符合條件的事件」作為目標

- 規格選擇每位使用者在某個時間窗內第一個符合條件的事件作為目標。Gusak et al. (RecSys 2025, §4.2) 顯示這種目標與前一筆事件的間隔較長，並建議不要使用。
- 規則：使用最後一筆事件（LOO），或使用 Last／Random／Successive 目標的 GTS。

### 4. 在截止點凍結的商品目錄，讓基線看不到歷史商品

- 商品目錄由截止點之前出現過的商品建立。較晚才首次出現的商品被排除在目錄之外，也就不在 ID 式基線看到的使用者歷史中；讀取文字的方法卻仍看得到這些商品的標題。
- 規則：逐方法、逐查詢計算可見歷史的商品數；數量必須一致，否則差異要標示為一個條件。

### 5. 沒有量測就斷言洩漏的方向

- 一份專案狀態紀錄寫道，LOO 下的跨使用者未來資料「只會提高」訓練式基線的分數。Ji et al. (TOIS 2023, 表 5) 報告兩個方向都有變化（例如 NeuMF NDCG@20 在 Amazon-electronic 為 −35.5% 至 +13.8%），名次也隨之改變。該紀錄已更正。
- 規則：只根據手邊資料的量測，寫下洩漏影響的方向；否則寫「方向未確定」，並規劃敏感度檢查。

### 6. 自行建立的 5-core 切分與官方切分不同

- 本地建立的 5-core LOO 切分，與某個公開評論資料集的官方 benchmark 切分不同；官方檔案在切分之前先對（使用者，商品）去重，保留最早的評論。在其中一個商品類別上，未去重而建立的 5-core 比官方 5-core 切分多保留了幾個百分點的使用者與商品；官方切分在使用者序列內沒有重複商品，歷史中也沒有測試目標。
- 規則：有官方切分時就下載，記錄雜湊值，並驗證使用者、商品與事件筆數、每位使用者的序列內沒有重複商品，以及沒有測試目標出現在自己的歷史中。

### 7. 依熱門度抽樣的負例，使 popularity 基線的結果反轉

- 有 50 個候選時，均勻隨機排序的 NDCG@10 期望值為 0.091。在依熱門度抽樣的負例下，popularity 排序器的分數低於這個值，因為最熱門的候選通常是負例。
- 規則：把依熱門度抽樣的負例當成反向壓力測試；要回答「方法是否依賴熱門度」，使用全排序、歷史對調對照，以及依目標熱門度分層。

### 8. 許多方法變體在報告用的使用者上相互比較

- prompt、讀取方式與歷史長度的變體，全都在同一批使用者上評分。逐人在各變體中挑最佳者（用目標挑選）的 oracle，帶來很大的增益，可部署的選擇器卻無法重現。
- 規則：在開發用使用者上調參，固定設定，再在新的使用者上報告；報告嘗試過的變體數量；絕不把逐人 oracle 選擇當作方法結果報告。

### 9. 執行失敗與方法失敗混在一起

- 記憶體不足的當機與伺服器錯誤，在早期的表格中被記為效用 0 的查詢。
- 規則：執行失敗重跑到成功；只有方法失敗（輸出無效或無法解析，或依設計無法排序）留在分母，效用為 0；在每個分數旁顯示失敗筆數。

### 10. 「確定性」方法的重複執行結果不同

- 一個本地的凍結模型，在相同輸入下的多次執行之間產生小幅的分數差異（當時原因未查明）；託管 API 重新查詢後，相當比例使用者的排序改變。
- 規則：宣稱某方法只需執行一次之前，先做確定性檢查（兩次相同的執行）；託管 API 的查詢在一個子集上重複。

### 11. 多次測試執行中最好的一次被採用

- 假設：託管模型每次執行的變動是雜訊，所以三次重複中取最高的一次沒有影響。
- 如何浮現：投稿前的審查發現，主表採用了開發用使用者上三次重複中最高的一次，而重複紀錄寫的是採用的列仍是原始的執行。
- 影響：指標上的差異很小，但這屬於測試集挑選，與「測試只評分一次」相矛盾。
- 規則：採用第一次預先登記的執行；把重複之間的變動當作可重現性的量測來報告；絕不依測試分數在多次執行中挑選。

### 12. 衍生表格讀取的檢查點比主表舊

- 假設：基線重新選參之後，每個分析都會讀到新的執行結果。
- 如何浮現：基線以較大的驗證樣本重新選參；主表使用新的檢查點，但融合對照與時間錨點比較仍讀取重新選參之前寫出的結果檔（同一個基線在相同使用者上的分數有明顯差異）。
- 規則：每個表格建構程式，都要斷言各基線列的檢查點識別（雜湊值或執行編號）與主表一致；重新選參會觸發每個衍生分析重跑。

### 13. 量化主張沒有轉移到替換後的資料集

- 假設：更換一個資料集，只會改變表格中的數字。
- 如何浮現：更換之後，內文中三個全稱界限（以固定數字搭配「至多」「從未超過」等詞）在新的或新增的資料上不成立。
- 規則：更換資料集之前，列出每個量化主張，並逐資料集重新驗證；優先使用指名資料集的範圍。

### 14. 請求時間協議在其中一個資料集上帶來大部分增益

- 假設：計算到請求時間為止的跨使用者統計，是公平的輸入，因為上線的服務看得到這些事件。
- 如何浮現：把統計量錨定在使用者最後一個可見事件時，方法的 NDCG@10 在其中一個資料集上大幅下降；使用時間匹配的負例時，低於兩個序列基線。相當比例的均勻負例在請求日之前沒有任何互動，請求時間的計數很容易排除它們。
- 規則：在正文報告預設協議與其理由，以及錨點和匹配負例的敏感度，同時量測相反方向的曝露（在 leave-one-out 下，訓練式基線的訓練資料有多少落在請求時間之後）。

### 15. 模型輸入帶有跨使用者資訊

- 假設：凍結模型相對於統計量的增量，量測的是模型從使用者自己的歷史與商品文字讀到什麼。
- 如何浮現：在兩個資料集上，選用的輸入加了一句關於其他使用者接下來是否選了該候選的描述；這句描述計入其他使用者同一天、列順序較早的事件，時間邊界比統計量使用的更寬鬆。
- 規則：選用的輸入旁，同時報告沒有跨使用者資訊的輸入所得的增量；每個元件使用同一個時間邊界，或逐一揭露。

### 16. 看過結果之後才放棄某個資料集

- 假設：論文可以保留最能說明方法的資料集。
- 如何浮現：兩個在書面事先承諾（「每個結果都納入比較」）下加入的資料集，差點被排除在計畫之外，而一個結果不利的舊資料集卻被移除。
- 規則：下載新資料集之前先寫下事先承諾，並遵守；移除既有資料集時，記錄一個獨立於其結果也成立的理由。

### 17. 託管模型在同一個名稱下改變

- 假設：託管端點的模型名稱代表一個固定的模型。
- 如何浮現：供應商在研究進行中把端點重新指向新模型；以重複雜訊下限做的重現檢查，顯示它是不同的模型。
- 規則：每個回應都儲存回傳的模型識別；每批新請求之前檢查識別；在新模型下重跑所有格子，並揭露這項改變。
