# /tc-review — 繁體中文台灣用語檢視

以台灣使用者和台灣工程師的角度，逐行檢視繁體中文輸出。

## 核心原則

1. **訊息保留最大化** — 不為了通順而刪減技術細節
2. **文字通順最大化** — 不為了保留訊息而寫出不自然的句子
3. **英文技術字詞原樣保留** — 指令、路徑、API 名稱、識別字不翻譯
4. **簡中零容忍** — 一處滲漏代表整段需重檢，不能只就該字替換

## 觸發時機

- 產出任何對外的繁中內容（README、文件、PR description 內的中文段落）
- 產出 plan file、review doc、handover doc 含中文時
- chat 回覆使用繁體中文時（每次回覆前的自我檢查）
- 使用者說「繁中檢視」「tc review」「台灣用語檢查」「幫我看繁中」

## 不適用

- 純英文輸出（code、commit message、PR description 本體）
- 程式碼註解刻意使用英文時
- 使用者明確要求簡體中文時

## 檢查清單

依序執行，每一步都要逐行掃描。

### 1. 簡中字形掃描

以下字根出現在輸出中即為紅旗，立刻停下整段重檢：

| 簡中字根 | 常見滲漏詞 | 台灣正確用法 |
|---|---|---|
| 设 | 设定、设置 | 設定 |
| 执 | 执行 | 執行 |
| 资 | 资料、资源 | 資料、資源 |
| 软 | 软件、软体 | 軟體 |
| 网 | 网络、网路 | 網路 |
| 档 / 文件(=file) | 文件（指 file 時） | 檔案（file）；文件（document）OK |
| 变 | 变量、变数 | 變數 |
| 函 | 函数 | 函式 |
| 参 | 参数 | 參數 / 引數 |
| 数 (simplified) | 数组 | 陣列 |
| 进 | 进程、异步 | 行程、非同步 |
| 异 | 异常、异步 | 例外、非同步 |
| 处 | 处理 | 處理 |
| 类 | 类、类型 | 類別、型別 |
| 体 | 软体 | 軟體 |
| 启 / 关 | 启动、关闭 | 啟動、關閉 |
| 单 | 菜单 | 選單 |
| 默 | 默认 | 預設 |
| 链 | 链接 | 連結 |
| 远 / 边 | 远程 | 遠端 |
| 栈 | 技术栈 | 技術堆疊 |
| 适 | 适配 | 適配 / 轉接 |

不只看字形 — 也看「用對繁體字但用了大陸構詞」的情況：
- 「軟件」→「軟體」（字是繁體但詞是大陸的）
- 「視頻」→「影片」
- 「內存」→「記憶體」
- 「硬盤」→「硬碟」
- 「信息」→「資訊」
- 「程序」→「程式」（指 program 時）
- 「服務器」→「伺服器」
- 「打印」→「列印」
- 「激活」→「啟用」
- 「優化」→ OK（台灣也用，但若語境是「最佳化」則用「最佳化」）

### 2. 中英夾雜掃描

規則：英文技術名詞（tool name、command、API、path）原樣保留，但不能在中文句子中間隨意插入英文普通詞彙。

**允許：**
- `Claude Code`、`Codex`、`Gemini CLI` — 工具專有名稱
- `SKILL.md`、`plugin.json`、`CLAUDE.md` — 檔案名稱
- `git push`、`npm install` — 指令
- `useMemo`、`AbortController` — 程式碼識別字
- `OAuth`、`API`、`CLI`、`PR`、`ADR` — 廣泛使用的縮寫

**不允許（改成中文或首次出現附帶說明）：**
- `leverage` → 用中文寫出意思
- `cap` → 上限
- `spike` → 突波 / 突然升高
- `lookup` → 查詢
- `regime` → 制度 / 機制
- `would_be` → 不要出現在中文句子裡
- `dep` / `deps` → 相依套件
- `var` → 變數
- `auth` → 驗證 / 授權（視語境）
- `repro` → 重現步驟
- `ETA` → 預計完成時間
- `nit` → 小問題
- `LGTM` → 可以合併 / 沒問題

首次使用的縮寫附帶中文說明：`OAuth（開放授權協定）`。之後可直接用 `OAuth`。

### 3. 語氣與通順度

- 專業、精確、技術導向 — 不用口語壓縮（「搞砸了」「炸了」「卡住了」「怪怪的」「踩雷」）
- 不用編輯式修飾（「完美」「搞定」「結論很驚人」「aha 找到了」）
- 不用比喻替代機制說明（「火力全開」「打到痛點」→ 寫出具體狀況）
- 句子讀起來自然，不像是「英文翻譯成中文」的機器翻譯腔
- 如果一個句子讀起來像是「把英文句子逐字翻成中文」，重寫成台灣工程師會怎麼講

### 4. 訊息完整度

- 壓縮或改寫不能刪掉技術條件（`may`、`must`、`usually`、版本、例外）
- 數字、路徑、指令、設定值必須保留原樣
- 如果原文有 qualifier（「通常」「可能」「視版本而定」），翻譯後也要有

## 輸出格式

檢視完畢後，回報：

```
## 繁中檢視結果

### 簡中滲漏
- [行/位置] 「X」→「Y」（原因）
- ...（無則寫「無」）

### 中英夾雜
- [行/位置] 「X」→ 改寫方式
- ...（無則寫「無」）

### 語氣 / 通順
- [行/位置] 原句 → 建議改寫
- ...（無則寫「無」）

### 訊息完整度
- 是否有技術細節在改寫中被刪除：是/否
- ...（無則寫「無」）

### 結論
- [ ] 可直接使用
- [ ] 需修正後使用（N 處）
```

如果是檢視自己剛寫的輸出（非檔案），直接修正後輸出修正版，不需要產出報告 — 報告是給檢視他人文件或檔案時用的。

## 自我檢查模式

每次以繁中回覆時，在送出前執行簡化版檢查：

1. 快速掃描有無簡中字根（§1 表格中的紅旗字）
2. 有無不必要的中英夾雜
3. 讀一遍確認通順 — 台灣工程師會不會這樣講？
4. 技術細節有沒有被漏掉

如果發現問題，修正後再送出。不需要告知使用者「我做了繁中檢查」— 這是預設行為，不是額外動作。
