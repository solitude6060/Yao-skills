# 預算與吞吐量

英文版 [budget-and-throughput.md](budget-and-throughput.md) 為執行規範。

依量測規劃成本，依結果能改變什麼排列工作，高成本的批次在規格確認後只啟動一次。執行期間的完整性（pid file、watchdog（監看程式）、不可變的輸入）屬於 `experiment-contract`；付費 API 帳本與共用硬體屬於 `research-lifecycle` 的運算資源參考檔（[../../research-lifecycle/references/compute-and-budget.zh.md](../../research-lifecycle/references/compute-and-budget.zh.md)）。

## 成本類別

每個類別分開記錄；效率主張寫明它比較的是哪些類別。

| 類別 | 內容 | 多久發生一次 |
|---|---|---|
| 前置準備 | 提供服務之前建好的統計量、索引、嵌入向量、快取 | 每次資料更新一次 |
| 選參 | 在驗證資料上搜尋係數、checkpoint（模型檢查點）或設定 | 每次選參一次 |
| 推論 | 每次請求的計算：呼叫次數、token（模型計算輸入長度的單位）、延遲、裝置記憶體 | 每次請求 |
| 重試 | 在宣告的規則下，方法失敗後的重複呼叫 | 每次失敗 |
| 更新 | 資料改變時重建前置準備或選參 | 每個更新週期 |

只比較延遲，不足以支持總成本的主張；寫明量測了哪些類別、在哪種硬體上。

## 由量測吞吐量估計執行時間

1. 用真實設定在一小部分真實輸入上執行（最大的候選集合、最長的輸入）。
2. 量測每小時處理的單位數與峰值記憶體。
3. 以規劃的單位數除以每小時處理的單位數，再加上模型載入與最後排名的時間；在批次確認之前，結果標為估計值。
4. 量到的記憶體允許時，平行執行彼此獨立的工作；宣告每個工作需要的記憶體。

由其他資料集或其他輸入長度換算而來的估計值，要標明這一點，並寫出它可能失準的原因。

## 最小的真實輸入能力檢查

批次之前，用真實輸入確認介面能做到計畫假設的事：輸入長度上限、最大候選數時的記憶體、方法需要的讀出或機率運算、輸出解析，以及介面的每次請求限制（例如除了 token，還有每次請求的圖片數）。通用案例：一個 set-wise（一次讀入整組候選）讀出方式在最大候選數時記憶體不足，佇列開始之後，批次中的每位使用者都失敗。

## 低成本試跑層與升級規則

- 保留一個低成本、廣泛的試跑層（小型硬體、少量使用者），給可能可行但尚未測試的變體使用。
- 在試跑之前寫好升級規則：哪種觀察會讓一個變體升級到昂貴層，以及由誰決定（例如兩位獨立的審查者意見一致）。
- 試跑層的結果用來選擇下一步要跑什麼；它們絕不進入結果表。
- 這個試跑層與篩選證據階段（`experiment-planning` 第 4 節）不同。在報告設定上只跑一次的結果是篩選階段的結果列：可以標上「篩選」收錄，但不支持穩健性或優越性的主張。

## 決策價值

依結果會改變什麼，排列待執行的工作。一旦成功就能取代整張矩陣的執行（例如一個較大的模型，若表現較好，會讓較小模型的矩陣過時）排第一。重要的執行還沒測試時，次要變體先等。

## 啟動高成本的重跑

1. 寫出完整規格：實驗卡、矩陣儲存格、輸入、版本、失敗處理、成本估計。
2. 擁有者確認規格；照原文記錄這次確認與其範圍。
3. 只啟動一次。同時執行與待決事項無關的部分。
4. 部分重跑之後又一次部分重跑，正是這個程序要防止的失誤。

## 通用案例

- 協定變更後的多次部分重跑，花費比一次確認過的完整重跑還多。
- 一次針對次要變體的長時間執行，延後了那個結果能取代整個比較的執行。
- 一個從另一個資料集線性換算、沒有在新輸入上量測任何片段的執行時間估計，是預約共用加速器的唯一依據。
