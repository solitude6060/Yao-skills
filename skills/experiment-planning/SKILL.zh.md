# 實驗規劃：實驗卡、對照組、矩陣、使用者群、預算

英文 [SKILL.md](SKILL.md) 是執行規範。參考檔：[references/experiment-card.zh.md](references/experiment-card.zh.md)（實驗卡、矩陣、追蹤表）、[references/control-design.zh.md](references/control-design.zh.md)（對照組設計）、[references/cohorts-and-exposure.zh.md](references/cohorts-and-exposure.zh.md)（使用者群與曝光紀錄）、[references/budget-and-throughput.zh.md](references/budget-and-throughput.zh.md)（預算與吞吐量）。

多數重跑來自三種批次：沒有回答任何寫明的問題、比較的方法看到的資訊不同，或在已經影響過方法設計的使用者上報告結果。寫程式或啟動之前，先寫好實驗卡與一張有追蹤的矩陣。

## 何時使用

- 實作方法變體、基線（baseline：比較對象）或分析之前，或啟動一個要花數小時或花錢的批次之前。
- 擴大使用者、候選集合、資料集或模型之前；協定變更、審查發現問題或某個關卡未通過之後。

不適用：推薦系統的切分、候選與指標規則，請用 `recsys-evaluation`；檢查一次執行是否符合約定並決定結果能否收錄，請用 [`experiment-contract`](../experiment-contract/SKILL.zh.md)；選擇研究方向，請用 [`research-ideation`](../research-ideation/SKILL.zh.md)。

## 1. 每個實驗一張卡

寫給專案外的讀者看；每個標籤第一次出現時都要說明。

| 欄位 | 內容 |
|---|---|
| 研究問題 | 它服務的研究問題，寫出名稱 |
| 目的 | 現在不知道什麼、為什麼重要 |
| 介入（intervention） | 唯一改變的那件事 |
| 最接近的簡單對照 | 能產生同樣結果、成本最低的替代做法 |
| 輸入與輸出 | 資料、使用者群、候選、模型、讀出方式（readout：從模型輸出取得分數的方法）；逐筆結果檔與指標 |
| 預期判讀 | 相對於一個指名比較對象的方向，以及會推翻主張的結果 |
| 成本 | 時間、記憶體、金額；已量測，或標為估計 |
| 會改變的決定 | 每種結果之後的下一步 |

沒有研究問題或沒有決定的卡，刪除。

## 2. 對照資訊，也對照架構

- 方法多讀了資訊而得到的增益，不能證明模型比較好。現在就規劃只用模型、只用輔助訊號、資訊對等（matched-information：比較雙方拿到相同證據）三種對照。
- 系統歸因（system attribution：整個方法勝過基線）不同於元件歸因（component attribution：某個元件造成增益）；後者需要移除或替換該元件。
- 固定參數的消融（ablation：拿掉某個元件，看效果掉多少；固定參數指其他設定不變）與重新選參的消融（拿掉後重新挑選設定）回答不同的問題；依主張需要規劃其中一種，並標明類型。
- 輔助訊號的界線寫成取用規則，例如允許計數統計量，不允許另一個已擬合模型的分數。

## 3. 一張矩陣加追蹤表

每個儲存格列一次：方法 × 資料集 × 條件 × 使用者群。追蹤表把每格標為完成、執行中或待做，並列出各方法的涵蓋情形，讓跳過某個條件的方法一眼可見。依階梯擴大：先少量使用者再增加、先小候選集合再加大、先用少數模型做出完整原型再加模型。

## 4. 證據階段與判讀

| 階段 | 執行次數與統計 | 能支持什麼 |
|---|---|---|
| 篩選（screening，迭代期） | 一次執行；點估計或配對差；不算區間 | 選擇下一個實驗；可收錄為標明「篩選」的結果列；不能支持穩健性或優越性主張 |
| 確認（confirmatory，最終主張） | 共同測試單位上配對差的不確定性（例如以使用者為單位的 bootstrap：重抽樣估計區間）；有訓練或解碼隨機性的方法，另外跑多個 seed（隨機種子）或重複執行，否則主張要寫明只根據一次訓練執行 | 寫進論文的主張 |

以單位為抽樣對象的 bootstrap 只涵蓋單位抽樣的變異，不涵蓋 seed 造成的變異。確定性（determinism：相同輸入得到相同輸出）要在寫明的執行環境下觀察，不能假設。不設任意的數字成功門檻：關卡是在驗證資料上與指名基線的比較，用平實的文字寫出。只有主張等價（equivalence）時，才在執行前宣告容許差距（margin）。

## 5. 使用者群、曝光紀錄、資訊對等

- 在第一個結果出來之前，保留開發群、報告群，必要時加上選參群。方法變體在開發群上挑選；設定在驗證目標上挑選（這些驗證目標可以屬於報告群，例如 leave-one-out（留一法：每位使用者的最後一筆事件作測試目標）；使用者互斥協定下不可以）；報告群的測試目標只評分一次。擴大樣本時，新樣本包含已經評估過的使用者；新加入的使用者另外報告。
- 宣稱某個使用者群是保留群（held out）之前，先清查它的曝光紀錄：所有讀過這些使用者目標的既有執行、分析與姊妹專案。
- 在協定裡寫明每個方法在訓練與推論時可以讀什麼。高嚴重度的協定問題，在主張定案前用實驗回答，不是靠搬動文字處理。

## 6. 基線

依方法類別挑選基線。每個基線用官方原始碼與官方設定執行；放寬的變體標明並列在官方版旁邊；只有原始碼本身會重新擬合（refit：選完設定後用訓練加驗證資料重訓）時才重新擬合。方法類別要給操作型定義：什麼從不更新、什麼在驗證資料上挑選、挑選要花多久。

## 7. 預算與啟動

- 用真實設定下量到的吞吐量估計執行時間；記憶體允許時，平行執行工作。
- 成本分類記錄：前置準備、選參、推論、重試、更新。
- 保留低成本試跑層（low-cost trial tier），並寫下升級到昂貴層的規則；試跑層的結果一律不進結果表。依決策價值排序工作：一旦成功就能取代整張矩陣的執行，排第一。
- 批次之前，用真實輸入檢查：輸入長度、最大規模下的記憶體、讀出方式、輸出解析。
- 昂貴的重跑由擁有者確認完整規格後一次啟動；與待決事項無關的安全部分同時進行。

## 輸出

實驗卡、矩陣與追蹤表寫進專案的計畫檔；確認後的規格交給 `experiment-contract` 做啟動前檢查（preflight）。以專案的聊天語言向擁有者回報。
