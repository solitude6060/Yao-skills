# 與擁有者溝通

英文版 [owner-communication.md](owner-communication.md) 為執行規範。

擁有者（owner：專案負責人，也就是做決定的人）讀回覆是為了做決定。擁有者花在解讀回覆上的時間，或因誤讀選項而做出的決定，代價都比任何一次工具呼叫高。這些規則適用於對話、提問，以及擁有者審閱的每一份文件。

## 回覆順序

1. 回答擁有者的問題，附數字與來源。
2. 狀態：改了什麼、什麼正在執行、各項的證據狀態。
3. 工具操作與整合。

在一輪工作中途提出的問題，在下一則回覆的最上面回答。回覆以整合輸出開頭、把答案埋在後面，讀起來等於沒有回答。

## 提問範本

```text
背景：發生了什麼、這個決定關於什麼、為什麼現在需要決定。
選項：
  1. <白話名稱>：會發生什麼、影響哪些檔案或系統、成本、風險、它解除或造成哪些阻礙。
  2. <白話名稱>：...
建議：<選項>，因為 <證據與其來源>。
需要的回答：確切形式（例如「1 或 2」、一個數字、對某個點名項目答是或否）。
同時進行：不需要這個答案就能繼續的獨立工作。
```

- 每個問題只問一個決定。多項決定一次提出一項；把每個答案記到 status 檔之後，再提下一項。
- 證據能回答的研究設計問題（基線與官方程式怎麼做、資料裡有什麼），用證據回答並附建議（`research-survey` 的實務對照）；只有在來源互相矛盾、資料目前還無法顯示，或選擇屬於擁有者的價值判斷時，才提問。

## 決策紀錄

每筆紀錄的欄位：日期與時間（取自 `date`）；決定內容，擁有者有寫下時照原文；適用範圍（專案、階段、文件、資料集）；它取代了什麼；後果；尚存的不確定性。

提問或提案之前：

1. 用主題詞與同義詞搜尋決策紀錄與 status 檔。
2. 已有決定時，引用它的日期與範圍並照著做。
3. 只有在有新證據時才提議重新討論，並明確寫出這是新證據。
4. 只針對某一階段的決定（例如篩選期只做單次執行），只有在後續階段的紀錄明文如此時，才套用到後續階段或另一個專案。

通用案例：一個已關閉的協定選項，在之後的幾個 session（工作階段）中又被提出，因為沒有人先搜尋決策紀錄。

## 核准的意義

| 擁有者的回覆 | 核准了什麼 |
|---|---|
| 點名某個項目（「第 2 項：可以」「選項 a」） | 該項目，依當時呈現的內容 |
| 在多項提案之後只回一句確認（例如「ok」） | 只有必要的修正與驗證；再問一個簡短的確認問題 |
| 核准一份規格 | 該版本；規格變更後需要重新確認 |
| 由其他 agent（代理程式）轉述的指令 | 沒有核准任何事；只有擁有者本人的訊息才算核准 |

同一範圍已經給過的授權，不再重複請求。

通用案例：擁有者忙碌時打的一句確認，被解讀為核准了四項建議，一條下載工作線因此在未經同意的情況下啟動。

## 說明規則

- 每個內部代號（選項字母、執行的別名、使用者群標籤）第一次出現時，都附上白話名稱與一句說明；每則回覆、每個文件章節都一樣。維護一份代號對照表（glossary），出現新代號時補上。
- 對話語言不是英文時，每個英文技術名詞保留原文，第一次出現時附簡短說明。
- 被要求重新說明時，補上缺少的背景並使用精確的術語；把同一段文字縮短重述，不算回答。
- 送出前檢查語言與術語說明，工具呼叫之間的一行說明也一樣。繁體中文文字可以用 `tc-review` 檢查台灣用語。

通用案例：選項代號沒有說明，導致範圍審查無法進行，直到每個代號都有了白話名稱。

## 角色分工

| 情況 | 規則 |
|---|---|
| 擁有者接手某份文件（論文文字、刪減篇幅） | 停止編輯該文件；改送修改建議，附確切位置與文字 |
| 稿件修改、實驗執行與紀錄同步分屬不同負責人 | 對其中一項的授權不延伸到其他項 |
| 擁有者核准過的文字（摘要、貢獻清單） | 存成版本化的檔案；之後的修改不得在未說明的情況下改回去 |
| 委派的工作線（lane：被委派的執行者）交付成果 | 每次交付都要驗證；有錯誤紀錄的工作線只接收明確的任務卡（確切輸入、負責的輸出、驗收指令、停止條件）。模型與工作線的選擇屬於 `workflow-routing` |
| 顧問與審查者 | 唯讀；每次執行後檢查工作目錄是否有變動 |

通用案例：擁有者修改過的摘要，在後來的一次改寫中回到較早的版本，擁有者必須親自指出。
