# 形式化驗證

英文 [SKILL.md](SKILL.md) 是執行規範。維護模式在 `references/maintain.md`。改編自
Lauren Tan 的 pstack `create-formal-verification-skill` 與
`maintain-formal-verification-skill`（MIT，`cursor/plugins` 的 `1ba91fc`，見 `LICENSE`）。

用在並行、重試、狀態機、parser 或 unsafe 程式碼光靠測試不夠時（「model-check 這個
race」「證明這個不變條件」），或既有形式化檢查涵蓋的程式碼改過、卻沒重新確認時。

測試只檢查有人想到要寫的案例；形式化驗證檢查一個明確範圍內的所有案例：模型中所有交錯順序、
某個上限內的所有輸入，或所有輸入。

## 從程式碼選目標

能從程式碼回答的就不問使用者。好目標是程式碼做出的承諾，壞掉會傷害使用者或結果，
測試又很少碰到：鎖協定、工作佇列、重試迴圈、狀態機、parser、跨執行緒或 rank 的 reduction。
選最強的目標，不選最好驗的。

## 讓問題決定工具

- 事件會不會以錯誤順序發生：對設計的小模型用 model checker，預設 TLA+／TLC。
- 程式本身對所有輸入是否正確（記憶體安全、溢位、資料結構不變條件）：用直接跑在程式碼上的
  verifier，例如 C/C++ 的 CBMC、ESBMC，Rust 的 Kani，或 SMT 驗證器。
- 該語言沒有 verifier：直說，改用 property-based testing 測真正的程式。
- 必須對任何規模成立：可能需要 proof assistant。

選開發者裝得起來的工具，鎖定版本，並說明理由。

## 好的驗證

貼近程式碼（模型每一部分都對得到可打開的程式碼，原子步驟一致）；會失敗（在故意弄壞的版本上
示範失敗）；發現就是發現（不為了通過而放寬性質或模型，使用者沒要求就不改產品程式碼）；
範圍誠實（說明上限、假設與沒涵蓋的部分）；不懂工具也看得懂（性質與傷害各一句話，反例寫成
程式碼用語的步驟）；重跑便宜（一個指令、鎖定版本、輸出放在持久位置而非 `/tmp`）；
與程式碼同步（記錄涵蓋的檔案與函式，以及最後確認的 commit）。

## 產生專案內的 skill

寫到專案的 skill 目錄（Claude Code 是 `.claude/skills/<area>/`，並放到其他 agent 讀得到
的位置），要有 frontmatter。下一個 agent 只看這份 skill 就要能判斷改動是否碰到受驗證的程式、
執行檢查、分辨真 bug 與建模錯誤，以及在有意改動時更新驗證。不留任何佔位符。
pstack 的 `statechart` 可把 TLC 結果畫成狀態圖，屬於選用的上游工具，不要把它的指令抄進來。

## 交付前先證明

照產生的 skill 走一次，在真實程式碼上做一個會破壞性質的暫時改動，必須被抓到；撤掉後確認
檢查回到原狀。抓不到就修 skill 或驗證，不是修暫時改動。

## 交付

回報驗證了什麼、用什麼工具與原因、上限、白話的發現、執行方式與沒涵蓋的部分。驗證與產生的
skill 跟產品修正分開提交。
