# 解釋這個數字

英文 [SKILL.md](SKILL.md) 是執行規範。效能數字的七個問題在 `references/benchmark-checklist.md`。
改編自 Lauren Tan 的 pstack `principle-explain-the-number` 與 `benchmark-checklist`
（MIT，`cursor/plugins` 的 `1ba91fc`，見 `LICENSE`）。

用在量測之前，以及相信、回報或根據一個量到的數字做決定之前：加速比、效能退步、吞吐量、
延遲、benchmark 或評估指標。數字要能說出「被什麼限制住」和「為什麼不是量到別的東西」，
才算結果。

## 跑之前

- 先寫下預計要報告的那一句話、會改變決定的結果、預期的雜訊範圍，以及比較設計
  （獨立執行，或依 seed、使用者、輸入成對）。在該設計下「差值」的不確定性大於效果時就停。
- 讀量測程式：它計時、計數、平均和忽略了什麼。
- 檢查機器負載：`uptime`、`nproc`，用到 GPU 時看 `nvidia-smi`。有其他工作在跑又停不掉時，
  兩邊交錯執行並註明。

## 四項義務

1. **為什麼不是兩倍？** 效能數字：用 profile 或執行中的系統計數器，找出限制結果的資源或
   程式路徑（核心、鎖、記憶體頻寬、磁碟、網路、GPU、data loader、壓測端），再對回原始碼；
   讀程式碼猜的不算。評估指標：改問是什麼限制了分數，例如資料涵蓋範圍（訓練中沒出現的
   item）、該協定下指標的上限、候選集大小、標註雜訊或協定本身；profiler 回答不了這個問題。
   機制還沒查明時，量測結果與未解釋的上限分開陳述。
2. **列出這個數字還可能在量什麼，逐一用證據排除**：錯誤或跳過的工作、快取、沒執行到的
   程式、沒調校的一方、雜訊、端到端占比太小的元件。評估指標另外查：split 之間的
   leakage（資料洩漏）、兩邊候選集或指標定義不同、baseline 用預設值、只跑一個 seed、
   有執行沒完成任務、差距只出現在單一模型或資料集（若是要寫明），並問這個情境是否重要。
3. **證明可重現**：效能至少每邊五次交錯執行，報中位數與範圍；評估指標跑多個 seed，
   報平均與變異或信賴區間，共用 seed、測試使用者或輸入時用成對比較。用「差值本身」在
   比較設計下的不確定性判斷（例如成對差值的信賴區間），不要只看各邊自己的變異：成對設計
   可以分辨遠小於各邊變異的差距。差值的區間包含 0 時，回報「無可量測差異」或「結論待定」。
4. **證據跟著數字走**：次數、變異、限制因素、指令、commit、資料版本寫進筆記、
   結果表或連結的檔案。

推薦系統指標另外套用 `recsys-evaluation`；要支撐論文主張的數字，專案自己的結果採納規則
照常適用。

## 回報

先講結論：較快、較慢、較好、較差、無可量測差異或結論待定。數字附單位、次數、範圍與
限制因素。效能結論：限制因素說不出來、有一方沒調校、沒算錯誤數、無法確認工作有執行，就寫
「結論待定」。評估結論：兩邊協定不同、有一方沒調校、沒有估計差值的不確定性，就寫
「結論待定」。兩者都要指出缺口。

使用者要的粗估跑一次即可，但仍要確認沒出錯、工作有執行，並註明只跑一次；那一次的結果
看起來不對，就做完整檢查。
在選項之間做選擇，永遠不算粗估。
