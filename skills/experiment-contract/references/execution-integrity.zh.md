# 執行完整性

英文版 [execution-integrity.md](execution-integrity.md) 為執行規範。

一次執行只有在它讀取的程式與輸入就是紀錄中的那些時才有效；也只有在它停下時有人察覺，才有用。這些規則同時處理這兩件事。

## 不可變的快照

- Shell 會在執行前預先讀入腳本。修改執行中的腳本，即使是長度相同的替換，也可能不會生效，所以被刪掉的條件仍可能執行。要改變執行中的佇列：停下佇列腳本，讓它不再啟動新工作；停下執行程式（runner）；依 pid 停下所有模型伺服器（被終止的執行程式可能讓它的伺服器繼續占用加速器）；在佇列紀錄檔中記下這次停止；再啟動一支只列出剩餘指令的新腳本。
- 絕不把封存檔解壓縮或把檔案複製到執行中工作正在讀取的輸入上。即使位元組完全相同，解壓縮也會就地重寫檔案，讀取者可能讀到寫到一半的檔案。跳過已存在且 checksum（校驗碼）相同的檔案，或解壓縮到暫存（staging）目錄，等沒有工作讀取這些輸入時再移到定位。
- 啟動前凍結執行所需的已準備輸入（資料、候選清單、設定），並讓執行指向凍結的副本。

## 啟動與等待

```bash
bash run_queue.sh > queue.log 2>&1 &
echo $! > queue.pid
ps -p "$(cat queue.pid)" && head -n 1 queue.log    # confirm the launch
```

用 `bash script.sh` 啟動，這樣缺少執行權限位元（execute bit）也不會讓啟動失敗。依 pid file（記錄行程編號的檔案）與行程狀態等待；zombie（殭屍行程：已結束但尚未被回收，狀態 `Z`）已經結束，但 `kill -0` 對它仍會成功：

```bash
pid=$(cat queue.pid)
while kill -0 "$pid" 2>/dev/null && ! ps -o stat= -p "$pid" | grep -q '^ *Z'; do
  sleep 30
done
```

等待工作在自己的紀錄檔中寫出結尾行，效果更好。絕不用 `pgrep -f '<command>'` 確認或等待：這個樣式也會比對到執行檢查的那個 shell 的指令列，於是失敗的啟動看起來像已確認，等待也永遠不會結束。

## Watchdog（監看程式）

佇列無人看管之前，設好一個在下列情況時結束（並因此發出通知）的 watchdog：

| 條件 | 常見原因 |
|---|---|
| 加速器閒置且沒有佇列行程 | 啟動失敗、佇列提早結束、等待程式錯過了結束 |
| 某一步比預期早很多結束 | 缺少輸入、權限錯誤、立即當掉 |
| 非零結束碼 | 任何失敗 |
| 同一個失敗重複出現 | 常駐程式（daemon）無限制地重試同一個失敗的工作 |
| 一段時間內紀錄檔沒有進展 | 卡住、傳輸停滯、等待程式在等一個殭屍行程 |

每次結束時找出根本原因，修正後重新設好。跳過失敗的工作不算修正。

## 重試

執行前宣告每個單位的重試次數。用完時，停下該單位並診斷；絕不無限制地迴圈，也絕不為了讓佇列繼續而跳過清單（manifest）或身分的不一致。每次嘗試都連同原因記錄；嘗試次數寫進該次執行的收據（receipt）。

## 進度回報

依執行實際產出的內容回報：已完成單位數與總數、紀錄檔最後一行與其時間、行程狀態。啟動指令的結束碼、存在的 pid，或存在的紀錄檔，都不是進度。紀錄中的時間取自 `date`；絕不估計。

## 通用案例

- 對執行中佇列腳本做的長度相同修改沒有生效，一個擁有者已取消的條件因此用掉了加速器時數。
- 一個封存檔被解壓縮到正在被讀取的輸入檔上，讀取者讀到寫到一半的檔案而失敗，佇列因此停下。
- 一個等待程式在等一個已成為殭屍行程的程序，從未觸發，損失了一整個夜間時段。
- 一個啟動檢查比對到它自己的指令列，失敗的啟動因此被回報為執行中。
- 一個常駐程式無限制地重試一個失敗的工作，佇列中其他工作只能等待。
