# 答案路徑稽核

英文版 [answer-path-audit.md](answer-path-audit.md) 為執行規範。

當增益看起來很大、很一致，或比預期便宜時，在寫任何文字之前執行。要問的是：從被保留的答案到分數之間，是否存在任何路徑。只有在下面每一條路徑都檢查過之後，「沒有找到」才算一個結果。

## 1. 逐元件的資料路徑

對方法的每個元件寫一列：

| 元件 | 讀取的欄位 | 每個欄位的來源 | 時間邊界 | 能否看到目標、它的評分、它的時間戳或之後的事件？ | 證據 |
|---|---|---|---|---|---|

- 所有元件使用同一個時間邊界。時間戳相同的事件依原始列順序排序，絕不依商品識別碼；檢查每個元件都用同一條規則。
- 請求時間的資訊：若某個元件讀取被保留事件的時間，比較的方法也必須拿到它；否則論文必須寫明這項不對稱，並用對照拿掉它。內部稽核評為 HIGH（高嚴重度）的問題，要用實驗回答（資訊對等對照），不能靠搬動文字處理。

## 2. 集合交集

計算並記錄每個交集的大小；計算之前先寫下預期值。

- 被評估的目標 ∩ 任何已擬合元件的訓練事件。
- 被評估的目標 ∩ 方法在推論時讀取的記憶、索引或統計量。
- 報告群使用者的測試目標 ∩ 用於開發或選參的目標（逐使用者 leave-one-out（留一法：每位使用者最後一筆事件作測試目標）下，同一批使用者可以提供驗證目標；使用者互斥協定（user-disjoint）下則不可以；他們的測試目標一律不可以），範圍包含本專案與共用資料的姊妹專案。
- 被重用的快取輸出 ∩ 相依項有改變的執行。

## 3. 獨立重算

用一支不 import 專案計分程式的腳本，從原始輸出重算主要數字。必須與回報的數字在印出的精度內一致。

## 4. 抽樣負例稽核

候選是抽樣而來時：

1. 寫下選出負例的規則（雜湊順序、熱門度、時間窗）。
2. 檢查目標是否經過同一條規則。若沒有，這條規則就能辨認出目標。
3. 只用這條選取規則替每份候選清單評分，不讀歷史、不用模型，並回報命中率與隨機期望值的比較。
4. 命中率遠高於隨機就是洩漏（leakage），即使目前的方法沒有用到它；之後的方法或模型可能會用到。修正抽樣器（均勻抽樣，或對目標套用同一條規則），並記錄這次稽核。

通用案例：負例是加鹽雜湊（salted hash）值最小的商品，目標卻不是；依反轉的雜湊排序，幾乎每位使用者的目標都排第一。

## 5. 識別碼稽核

若商品或使用者識別碼出現在模型輸入中：

- 用只看識別碼的規則（最大 id、最小 id、清單中的 id 順序）替同一批候選評分；
- 這條規則的分數必須接近隨機。若不是，從輸入中移除識別碼並重跑。

通用案例：在新商品的候選池上，一條不讀任何歷史的「最大 id」規則，分數遠高於隨機。

## 6. 跨模型家族審查

把稽核表、交集數量與程式路徑，交給至少一位來自其他模型家族、在全新上下文中的審查者。請它找出表格漏掉的路徑。接受或否決每一條回報的路徑之前，先對照程式查證（[finding-triage.zh.md](finding-triage.zh.md)）。

## 紀錄

稽核紀錄列出上面每一節與其結果、使用的指令，以及沒有檢查的項目。被跳過的一節寫成「未檢查」；絕不概括為「沒有洩漏」。
