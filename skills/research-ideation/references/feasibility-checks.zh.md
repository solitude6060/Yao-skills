# 用真實資料檢查可行性

英文版 [feasibility-checks.md](feasibility-checks.md) 為執行規範。

在投入一個題目之前執行。每項檢查在手邊已有的資料上只需幾分鐘到幾小時，而每一項都曾讓某個題目停止或轉向，否則要多花好幾週。把它們寫成一支程式並存下輸出，讓新的 session（工作階段）能重跑程式，並與存檔結果比對（diff）。

## 檢查項目

| 檢查 | 怎麼做 | 何時調整或停止 | 通用案例 |
|---|---|---|---|
| 1. 需要的模態或欄位存在 | 在方法實際讀取的來源中，計算有該欄位的商品數；確認比較中的每個方法都使用它 | 方法本身，或主張所依賴的某個方法，沒有使用這個模態 | 一個多模態計畫在發現第二個方法完全不使用圖片後停止 |
| 2. 定義性的數量成立 | 在實際的時間與同分規則下，計算定義主張的母體（例如在請求當下是新商品或冷啟動的目標） | 母體太小撐不起主張，或大多與它的標籤不符 | 大多數在請求當下被標為「新」的目標，在請求之前就已經有互動；真正冷啟動的子集只占一小部分 |
| 3. 最直接的變體尚未飽和 | 執行這個想法最便宜的版本，例如在輸出端對現有訊號做學習式重組，再加上一個逐查詢挑較好來源的 oracle（理想選擇器）當作上界 | 便宜的變體幾乎不改變指標，且與 oracle 的差距很小 | 在輸出端對同一組訊號做學習式重組，指標最多只變動幾個百分點，計畫因此改用另一種機制 |
| 4. 機制能與較簡單的替代做法不同 | 推導，或在小樣本上模擬，所提的機制能否產生較簡單的替代做法無法產生的輸出 | 在模型的形式下兩者等價，任何實驗都無法區分 | 推導顯示，透過商品嵌入向量（embedding）做引導，只能在嵌入向量張成的空間（span）內改變分數，因此無法重現 late fusion（後期融合：各自算分再加總）給每個商品的加分；這項比較因此有資訊價值 |
| 5. 最接近與同期的作品已知 | `research-survey` 的全景調查與同期作品追蹤模式 | 已發表的作品在相同情境下做了同樣的事 | 一篇 preprint（預印本）已經把同樣的統計量寫成文字放進模型輸入，並回報模型必須經過訓練才讀得懂 |
| 6. 實作存在 | 程式（官方或可信來源、版本、授權）、已釋出的 checkpoint（模型檢查點）與其訓練資料、資料取得方式、各自評估時用的協定 | 某個關鍵元件無法重現 | 在選定初步研究路線之前，先盤點候選基礎模型的程式、checkpoint 與協定 |
| 7. 資源足夠 | 運算資源、付費 API 餘額，以及本題目目前有效的資源限制 | 第一階段需要擁有者尚未授權的資源 | 一個初步研究只用雲端代管的 API 規劃，因為本地加速器保留給另一個專案 |
| 8. 沿用的數字能重現 | 重跑產生本題目所依據數字的程式，並與存檔輸出比對 | 數字無法重現 | 一個新題目的第一個指令，就是重跑沿用的可行性程式，並與存檔輸出比對 |

## 記錄方式

- 一支程式計算所有檢查；它的輸出存在旁邊；起始文件同時引用兩者。
- 每項檢查寫明它保護的研究問題。
- 未通過的檢查連同數字記為證據，透過決策紀錄讓題目進入調整或停止。未通過的檢查絕不用較寬鬆的定義重跑來讓它通過。
